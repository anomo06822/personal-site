最近整理自己的 AI 工作流時，我做了一個決定：退役自己維護的 Content Studio，把研究與草稿交回 Heptabase，讓 Codex 負責產製與執行，再透過 Git 和 personal-site 發佈。

這個決定來自一個很實際的問題：當筆記、任務、文章和發佈狀態散在不同地方，我需要花多少力氣，才能確認眼前這份內容是不是最新的？

自己做一個整合平台，可以把功能放進同一個畫面，卻也要承擔編輯器、資料模型、同步、登入與背景服務的維護。我開始重新分配責任：每一種資料有明確的主要保存位置，每一段工作有可檢查的交接結果。

## 先決定資料歸誰，再決定怎麼自動化

我目前採用的分工如下。這是依照個人研究、開發與寫作需求做出的選擇，並不代表每項工具只能做表中的事情。

| 工具 | 在我工作流裡的責任 | 主要保存或交付的東西 |
| --- | --- | --- |
| Zotero | 保存文獻原件與書目 | 論文資訊、DOI／版本、可取得的 PDF、閱讀卡連結 |
| Heptabase | 累積理解與編輯內容 | 研究比較、知識關聯、決策、選題與可編輯草稿 |
| Linear | 追蹤需要交付的工作 | 專案、issue、優先級、負責人、依賴、驗收條件與狀態 |
| Codex | 理解需求並執行 | 查找資料、寫程式、整理文章、呼叫工具、驗證與按需排程 |
| image_gen | 製作文章視覺素材 | 由 Codex 協調生成、經人工審閱的封面圖 |
| Bitwarden Secrets Manager | 管理程式需要的機密 | API key、服務 token，以及受限程序的憑證存取 |
| Slack | 承接協作溝通 | 討論、原始對話連結，以及指定對象的通知 |
| Git／GitHub | 保存可追溯的交付版本 | 程式、核准後的文章與圖片、變更紀錄 |
| GitHub Actions／Pages | 建置與部署 | 指定 commit 的執行結果、可存取的網站 |
| personal-site | 作為公開內容的主要入口 | 中英文文章、固定網址與作品脈絡 |
| LinkedIn／X | 按需分發內容 | 指定渠道的文案與文章連結 |
| GA4 | 觀察發佈後的回饋 | 文章閱讀情況與流量來源資料 |

表格看起來仍有不少工具，但一次工作通常只會經過其中幾個。工具多寡並不是我唯一在意的事；更直接的檢查方式是：要修正一項資訊時，我是否知道應該改哪裡。

## Zotero 保存文獻，Heptabase 保存我的理解

研究一個題目時，我把論文書目與 PDF 放在 Zotero，把閱讀後的比較、疑問和判斷留在 Heptabase。Zotero 本身支援書目、附件、集合與標籤，適合承接這一層資料管理。[Zotero 官方入門文件](https://www.zotero.org/support/quick_start_guide)

例如整理 AI Agent 的記憶設計，我會先確認引用的是哪一篇論文、哪個版本，再整理不同方法如何使用記憶、各自的限制，以及哪些做法值得用在自己的專案。前者需要可靠的文獻紀錄，後者需要持續修改與連結的思考空間。

我已經把 Zotero 與 Heptabase 的文獻流程接起來。需要補充研究時，由 Codex 先查既有項目，保存選定文獻、確認附件，再依需要觸發與核對 Heptabase 同步。同步後的來源卡和 PDF 方便閱讀；我自己的比較與結論仍有獨立的知識脈絡。

這也留下清楚的查證路徑：文章裡的一個判斷，可以回到研究筆記，再回到原始文獻。檔案進入知識庫之後，內容是否完整、論點是否成立，仍需要檢查。

## Linear 記錄承諾，Codex 推進工作

我會把需要追蹤交付的事情放進 Linear：要完成什麼、先做哪件事、依賴誰，以及什麼證據代表完成。這與 Linear 用 issue 表示具體工作、用 project 組織交付成果的模型相符。[Linear 官方概念說明](https://linear.app/docs/conceptual-model)

Heptabase 可以保留「為什麼選這個方案」，Linear 則保存「這個方案目前做到哪裡」。兩者用連結交接，減少同一份進度在多個地方更新。

例如某份研究指出一個 API 設計需要調整，我會在需要正式追蹤時，讓 Linear issue 連到相關研究，寫清楚驗收條件，再交給 Codex 實作、測試與整理差異。完成後，經授權把程式變更和驗證結果回到同一個 issue；值得重用的設計結論則留在 Heptabase。

單純準備一篇文章，不需要為了符合流程而先開 issue。只有涉及期限、協作或明確的交付追蹤時，Linear 才加入這條路徑。

Codex 是日常執行入口。我描述預期成果，它依當次需求選工具並完成可驗證的產物。重複出現的步驟寫成 skill；有定時需求時才安排排程。知識與任務狀態各有保存位置，讓下一次工作能接續，而不必完全依靠上一段對話。

## 發文流程：先看完整產物，再決定上線

我的內容流程現在定義為：

**Heptabase 草稿 → Codex 產製文章與圖片 → 我審閱 → Git push → GitHub Actions 建置與部署 → 驗證公開頁面。**

我把這段流程整理成發文 skill。當我說「準備發文」，Codex 要交付的包含完整正文、中英文版本、實際封面圖、來源查核摘要，以及這次要發到哪些地方。只看摘要，無法知道正文有沒有把我的意思寫偏；只看圖片提示詞，也無法判斷最後的圖片能不能用。

審閱包因此要放進真正準備發佈的內容。我確認這一版之後，才進行 Git 提交與推送，沿用網站的 GitHub Actions／Pages 部署流程。GitHub Pages 支援由自訂 Actions workflow 建置及部署網站。[GitHub 官方文件](https://docs.github.com/en/pages/getting-started-with-github-pages/using-custom-workflows-with-github-pages)

這裡有兩個我在意的交接點。第一，確認之後發出的文章與圖片，必須是我剛才看過的版本；若內容改了，就應該按新版本處理。第二，push 成功之後，還要核對部署結果和公開頁面，才能回報上線完成。

預設目的地是 personal-site。需要分享到 LinkedIn 或 X 時，再準備並確認對應文案。文章的正式網址留在自己的網站，社群負責把讀者帶到內容；封面目前用在網站與分享預覽，原生圖片貼文則屬於另外需要確認的發佈方式。

## 憑證、溝通與成效，也各自有位置

程式憑證交給 Bitwarden Secrets Manager，執行時才透過受限的程序取得。Bitwarden 官方提供的 CLI 就包含向應用程式注入 secrets 的用途。[Bitwarden Secrets Manager 說明](https://bitwarden.com/help/secrets-manager-overview/)

這讓研究筆記可以記下某個服務的用途與設定狀態，而不用把 token 混進文章草稿、任務描述或聊天紀錄。

Slack 負責協作討論，以及我明確指定的通知。需要長期保存的決策回到 Heptabase，需要追蹤的交付回到 Linear，並保留原對話連結。一次內容工作沒有溝通需求，就不必額外產生通知。

GA4 被放在發佈之後的回饋環節，用來觀察文章被閱讀的情況與流量來源，協助下一輪選題。社群授權和成效資料存取仍需要有效憑證與實際連線驗證；在這些條件完成前，我不會把它描述成已持續運作的自動化。

## Content Studio 退役後，保留下來的是哪些能力

這次調整已把 Content Studio 和 AIPW 執行服務從目前工作樹移除，保留歷史內容與資料。發佈、失敗重試和成效同步的程式移到 personal-site，草稿編輯回到 Heptabase。

新的發佈工具已完成本機與隔離測試；截至這篇草稿整理時，工具改動仍待正式提交與部署驗證。這是一個正在落地的個人工作流，還沒有足夠的使用數據可以宣稱節省了多少時間。

我願意保留的自製程式，集中在現有工具之間需要精確交接的地方：固定發佈版本、記錄執行結果、從失敗步驟恢復，以及確認網站真的更新。這些能力直接服務於交付，也比較容易定義怎麼驗收。

接下來，我會用幾個具體問題檢查這次調整：一篇文章能否找回原始依據？工作狀態是否只需要更新一次？審閱後的版本是否確實上線？出錯後能否接著做，而不用重來？

當這些問題都有可查的答案，我才能把更多注意力放回研究、實作與寫作本身。
